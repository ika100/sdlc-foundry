# Spec: this repo's slice of a system plan

Read from `/component:spec --from-plan <plan> [<repo-id>]` (section D), by hand: `/system:ship` writes and approves a repo's spec itself (`cplat system ship repo start`, spec 155). The plan lives in the gitops-app repo (`docs/plan/<spec_id>.md`, ADR-011/026); never edit it from here, since that repo owns it.

1. `<repo-id>` defaults to this repo's name (or `repo` in `.platform-app.yml`). Run `cplat spec new --from-plan <abs plan path> <repo-id>` (add `--no-shape` in a repo without a shape): it writes this repo's spec with the system's problem, a **System context** section (the system criteria assigned to this repo, the contract, notes) and `parent:` set. Then `git checkout -b feature/<spec_id>`.
2. **The plan wrote this repo's criteria** (spec 147: the new spec already has criteria, each naming its `(system AC-<NNN>.<n>)`, and no open questions): no product-manager. Run `cplat spec check <id>`, show the criteria and ask for the approval. Then continue with step 3 or the plan and build. Otherwise (a plan written before spec 147):
   **product-manager**: `MODE: new`, `SPEC_DIR`, and "the System context section is binding: write this repo's criteria so that together they implement each listed system criterion and follow the contract; every criterion names the system criterion it serves, `(system AC-<NNN>.<n>)`". Then `cplat spec check`, and section B from step 5 on (questions loop, commit, finish).
3. Remind the user that `/system:ship` (or `/system:spec done <id> <repo-id>`, in the gitops-app repo) records the repo as done after its PR merges.
