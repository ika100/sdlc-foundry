## Risks (not verdicts, but should be checked before release)

- **The `cplat_run_id` label.** `OTEL_RESOURCE_ATTRIBUTES` sets OTel *resource* attributes. Prometheus' OTLP receiver does not make resource attributes into series labels by default; it puts them on `target_info` unless `otlp.promote_resource_attributes` (or `promote_all_resource_attributes`) lists them. The design says the pairs land "on every datapoint", and the tests fake the store, so nothing proves `{cplat_run_id="..."}` matches in otel-lgtm 0.35.0. If the label is only on `target_info`, the per-run dashboard panels are empty and `compare` always returns no figures. That would fall back silently to AC-101.10, so AC-101.9 would never happen in practice. One end-to-end check on a kind cluster (`claude_code_token_usage_tokens_total` in Grafana Explore, looking for a `cplat_run_id` label) settles it. If the label is missing: promote the `cplat.*` attributes in the stack's Prometheus config, or join on `target_info`.
- **Signal-specific endpoints from the user's shell.** `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` / `..._LOGS_ENDPOINT` take precedence over `OTEL_EXPORTER_OTLP_ENDPOINT`, and `OTEL_EXPORTER_OTLP_HEADERS` passes through. If the user's environment has a remote one, cplat turning telemetry on would export there without `allow_remote`. Suggested fix: set the signal-specific endpoints from the checked endpoint too (`<endpoint>/v1/metrics`, `/v1/logs`).
- `compare` reads `query_url` and the context from `Path.cwd()` (`telemetry.py:288`, `:292`), not the run's repo. That only matters for the project settings file when cplat runs from another directory.
