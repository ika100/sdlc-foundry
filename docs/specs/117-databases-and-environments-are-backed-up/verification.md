## Choices the coders made where design.md is silent

1. **`--to latest` is refused when there is no restore point** (`dbrestore.py:218-220`: `earliest none, latest none`). design.md: "`--to` outside the window … (`none` for both when there is no restore point)", and for `latest` "the active cluster" as the source. Restoring "latest" from a store with no base backup cannot work, and the refusal uses the designed text. No conflict.
2. **The "available" list of `system restore`.**
   - *First review:* it listed every backup, and any listed name was accepted, so with `--replace` the volumes of a failed backup would be deleted before Velero rejected the Restore.
   - *Now (da7c6a3):* only `Completed`/`PartiallyFailed` backups are listed as available, and any other backup is refused before any read of volumes or any write. This is consistent with design.md (`available: <names newest first>`; `latest` = the newest `Completed`), and no longer a risk.
3. **What "started" waits for.**
   - *First review:* it waited only until the workload root existed.
   - *Now (da7c6a3):* it waits for the rollout of Deployments, StatefulSets and DaemonSets, and for anything else until it exists. That matches design.md's "wait for the workloads".
4. **The `--json` shapes.** `resource restore --json` prints the `Report`, which is what design.md specifies ("`--json` prints the Report"); `r.data` adds `result`/`cluster`. For `system restore --json` the design is silent: the command prints `{result, backup, namespace, text}` (or `{result: listed, backups}`). The new refusal prints `{result: refused, backup, namespace, text}`. No conflict.
