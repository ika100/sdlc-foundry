**A Java library shape: `/component:new <name> <description> --type library --lang java` (#718).** Code shared by several Java services had no managed home: Java offered only the Spring Boot service. The new `library-java` shape creates a plain Maven library `<group_id>:<project_name>`: JDK 21, the service's tooling and gates (Spotless + Checkstyle + compile, JUnit 5 with an 80 % JaCoCo line gate, trivy or OWASP Dependency-Check + detect-secrets), a sources jar, no Spring Boot, no image and no deployment. A release tag deploys it to GitHub Packages (`maven.pkg.github.com/<owner>/<repo>`) through the `publish` CI job and `devbox run publish vX.Y.Z [--dry-run]` ([ADR-125](../adr/125-library-releases-publish-to-github-on-the-tag.md)): the tag is the version (`pom.xml` keeps `0.0.0-SNAPSHOT` and `/component:release` writes only the CHANGELOG), a commit that is not the tagged one publishes nothing, and a rerun of the same tag is a no-op. The library's `CLAUDE.md` says how another repo depends on it (the `github` repository, a `read:packages` token as the Maven server, `PACKAGES_READ_TOKEN` in CI). The `svc-java` agents (0.9.0) serve both Java shapes; a system's `system.yaml` accepts `type: library, lang: java`. Detection changed: a bare `pom.xml` is now a Java library, while one next to a `Dockerfile` or referencing Spring Boot (and any Gradle build) stays `service-java`. Update the plugins (`/plugin marketplace update`) to get `svc-java` 0.9.0 ([spec 217](../specs/217-a-java-library-shape/spec.md)).
