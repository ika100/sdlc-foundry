**`/component:release` tags the commit staging runs and writes the CHANGELOG and the next development version after the tag (#426).** The release used to merge a release PR (version bump and CHANGELOG) and tag its merge commit: a new build staging never tested, so the prod promotion refused its digest ([spec 106](../specs/106-prod-runs-the-exact-image-staging-tested/spec.md)). Now `cplat component release target` decides the commit: the one staging pins (`sha-<40>`), or `main`'s head for a component without staging (a library, or a repo not linked to a gitops-app). It refuses, naming the staging commit, the candidate commit and the next step, when staging has no instance, does not pin a `sha-<40>` build, runs a commit that is not on `main` or is already released, or nothing is new since the last release. The gates run on that commit, the tag waits for `main`'s `ci` run on it, and the release agent then opens a follow-up PR with the CHANGELOG entry and the next development version (Python `X.Y.(Z+1).dev0`, Java `X.Y.(Z+1)-SNAPSHOT`, web `X.Y.(Z+1)-dev.0`, Go none), merged after green CI and never tagged. The tagged commit's version file therefore shows the previous development version; the release version is the tag, the image's `X.Y.Z` tag and the CHANGELOG, and the summary says which commit was tagged and why. New `library-python` repos read their version from the git tag (`hatch-vcs`), new `service-python` repos read `__version__` and the app's version from `pyproject.toml` ([spec 138](../specs/138-release-tags-the-staging-build/spec.md)). Update the plugins (`/plugin marketplace update`).
