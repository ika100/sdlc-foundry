**The release waits for an upgrade render check and a shorter upgrade e2e, and the oldest supported release is tested nightly (#400).** The upgrade e2e ran the platform update and the Postgres 16 to 17 drill in one job (22 to 25 minutes), and only from the previous release. Now `upgrade render check` (`uv run scripts/upgrade-render-check.py [--from <tag>]`, seconds, no cluster) compares, from the previous and the oldest supported release, the render of the old system with the same system after `/platform:update` and fails on changes Kubernetes cannot apply in place or that lose data. `e2e upgrade (previous release → candidate)` runs the platform update part only; `e2e upgrade (oldest supported release → candidate)` runs nightly and on dispatch, and the Postgres drill has its own workflow (`e2e-upgrade-drill.yml`, `e2e upgrade drill (Postgres 16 → 17)`) that runs nightly and on the changes that touch it. `release-check.py gate` requires the render check and the previous-release job only. A deliberate breaking change is accepted with a changelog line `Upgrade step: <Kind> <field>: <what the system owner does>` ([ADR-116](../adr/116-upgrade-tests-split-a-fast-release-gate-from-nightly-runs.md), [spec 191](../specs/191-upgrades-are-tested-fast-across-skipped/spec.md)). **Action:** none for system owners; when you jump several releases, read the `Upgrade step:` lines of the releases you skip.
