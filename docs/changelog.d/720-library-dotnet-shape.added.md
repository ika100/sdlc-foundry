**A .NET library shape: `/component:new <name> <description> --type library --lang csharp` (#720).** Code shared by several .NET services had no managed home: .NET offered only the ASP.NET Core service. The new `library-dotnet` shape creates a C# library packed as the NuGet package `<Namespace>` (the PascalCase project name) for the pinned .NET 10 LTS: the service's tooling and gates (`dotnet format` + the .NET analyzers with warnings as errors, xUnit with an 80 % coverlet line gate, trivy over the NuGet lock files + detect-secrets), one packable project and its tests, no ASP.NET Core, no image and no deployment. A release tag pushes it to GitHub Packages (`nuget.pkg.github.com/<owner>/index.json`) through the `publish` CI job and `devbox run publish vX.Y.Z [--dry-run]` ([ADR-125](../adr/125-library-releases-publish-to-github-on-the-tag.md)): the tag is the version (the project keeps `0.0.0-dev` and `/component:release` writes only the CHANGELOG), a commit that is not the tagged one publishes nothing, a rerun of the same tag is a no-op, and the token reaches NuGet through a temporary config and `NUGET_API_KEY`, never the repo or the command line. The library's `CLAUDE.md` says how another repo uses it (a `nuget.config` source with a `read:packages` token, `PACKAGES_READ_TOKEN` in CI, the `PackageVersion`/`PackageReference` lines). The `svc-dotnet` agents (0.1.1) serve both .NET shapes; a system's `system.yaml` accepts `type: library, lang: csharp`. Detection changed: a .NET solution or project without a `Dockerfile` is now a .NET library; with one it stays `service-dotnet`. Update the plugins (`/plugin marketplace update`) to get `svc-dotnet` 0.1.1 ([spec 221](../specs/221-a-net-library-shape/spec.md)).
