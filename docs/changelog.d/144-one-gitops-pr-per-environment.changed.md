**A system ship changes dev in one gitops PR, and staging in one more (spec 144).** A system spec across the gitops repo and two components gave dev three PRs (the entry, then one `pin-dev` PR per component), each a CI round, a merge and an Argo CD sync, and with staging on `promote: after-dev-smoke` one staging PR per component as well. Now the gitops entry's `compose/<spec>` PR stays open (`cplat system ship entry land` only waits for its checks), each component ship pushes a marker `ship/<spec>/<component>-<sha7>` when it merged so the gitops-app's `pin-dev` opens no PR for that build, and ends its deploy at "pinned in the system ship's dev PR" once its image is built; the system ship pins every build on `compose/<spec>`, and the new `cplat system ship land` merges that one PR after the last component, waits once for Argo CD, runs every component's dev smoke (as `cplat instance verify dev` records it) and promotes staging for the whole spec in one PR. A component that escalates keeps the PR unmerged, so dev never runs a partial spec. Merges outside a system ship are pinned as before ([spec 144](../specs/144-one-gitops-pr-per-environment-for-a/spec.md), [ADR-083](../adr/083-a-system-ship-lands-each-environment-in-one-gitops-pr.md)). **Action:** run `/platform:update` in each gitops-app to get the new `pin-dev.yml` (until then a system ship keeps one dev PR per component and says so), and update the plugins (`/plugin marketplace update`).
