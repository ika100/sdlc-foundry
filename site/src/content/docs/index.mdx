## Platform glue should not cost a small team months

<CardGrid>
  <Card title="The problem" icon="warning">
    Every service needs CI, a hardened Dockerfile, Kubernetes manifests, secrets, observability, policy and a promotion path. Small teams rebuild it per repo, and LLM agents that improvise it make it inconsistent faster. [Read the problem statement](/sdlc-foundry/problem/).
  </Card>
  <Card title="The approach" icon="rocket">
    Opinionated templates and a tested CLI do the deterministic work; Claude Code agents orchestrate it and ask before anything outward-facing. The GitOps repo owns every manifest, rendered from one declarative file. [Read the vision](/sdlc-foundry/vision/).
  </Card>
  <Card title="The value" icon="star">
    One slash command creates a repo that already builds, scans and publishes images. Adding Postgres, secrets or observability is one declaration. Promotion is a pull request you can review. [See the client value](/sdlc-foundry/value/).
  </Card>
</CardGrid>

## A model you can hold in your head

A **system** is made of **components** (services, websites, libraries), the **APIs** between them and the **resources** they use. Each part runs once per **environment** as an **instance**, and promoting moves a version one cell to the right. Every command is named after the noun it acts on: `/system:new`, `/component:add`, `/resource:add`, `/instance:promote`.

## From an issue to production

You decide at three points: route an issue, approve its spec, promote to prod. `/component:ship` runs everything in the green band, and every run, failure and alert comes back as an issue for the next round.

## Optional: see it all in one place

Everything runs from Claude Code. If you want an overview, `/platform:ui` opens a local console in your browser. The **Inbox** shows the few decisions that need you, the **Board** every change by stage, and **System** where each part runs at which version. Each decision shows what it changes, the exact command, and the way back; the console stores nothing and every change ends in a pull request. Help, the process and every command are built in: press `?` or `g`.

## One declaration, a running stack

<div class="split">
<div>

```yaml title="applications/shop/system.yaml"
# abbreviated: /component:add fills in port, probes, user and resources from the component type's defaults
system: shop
owner: team-shop
components:
  shop-api:
    type: service
    lang: java
    repo: acme/shop-api
    uses: [postgres]
    secrets:
      - name: shop-api-auth
        generate: [JWT_KEY]
    instances: {dev: {}, staging: {}}
  shop-web:
    type: website
    lang: typescript
    repo: acme/shop-web
    env: { API_URL: "http://shop-api" }
    expose: true
resources:
  postgres: {type: database}
```

</div>
<div>

From that file the platform renders, per environment: Deployments with numeric non-root users and read-only filesystems, Services, Gateway API routes, an `ExternalSecret` that creates the JWT key in the cluster, a CloudNativePG database whose connection string reaches `shop-api` as `DATABASE_URL`, an OpenTelemetry collector, and Kyverno policies that check all of it. ArgoCD syncs the result. Nothing is applied by hand, and no secret value touches git.

[How it works](/sdlc-foundry/guides/how-it-works/) · [Configuration reference](/sdlc-foundry/reference/configuration/)

</div>
</div>

## What you get

<CardGrid>
  <Card title="Scaffold any shape" icon="document">
    `/component:new` creates Python, Java, Go and Next.js services, libraries and the GitOps repo from tested templates, with CI, Dockerfile, devbox recipes and agent instructions. [Shapes](/sdlc-foundry/reference/shapes/)
  </Card>
  <Card title="Agent pipeline" icon="random">
    `/component:spec`, `/component:plan` and `/component:build` go from an approved spec to failing acceptance tests, code that passes them, a check against every criterion and a pull request, with the right agents for each shape. [Agents model](/sdlc-foundry/guides/agents/)
  </Card>
  <Card title="GitOps that is generated" icon="setting">
    `/component:add` edits one `system.yaml`; `render.py` writes every manifest. `/instance:promote` pins verified image tags per environment. [Concepts](/sdlc-foundry/concepts/)
  </Card>
  <Card title="Secrets without git" icon="approve-check">
    External Secrets Operator creates and reads secrets in the cluster; generated passwords never leave it. [Secrets](/sdlc-foundry/concepts/secrets/)
  </Card>
  <Card title="Resources and observability" icon="seti:db">
    Postgres via CloudNativePG; OpenTelemetry collector with optional Grafana dev stack. [Resources](/sdlc-foundry/concepts/addons/)
  </Card>
  <Card title="Guard rails" icon="seti:lock">
    Kyverno policies for the platform's own conventions, checked before merge; pinned Actions, scanned images and SBOMs. [Guard rails](/sdlc-foundry/concepts/guard-rails/)
  </Card>
</CardGrid>
