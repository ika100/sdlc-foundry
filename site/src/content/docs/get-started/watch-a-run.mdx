One system, recorded in one run from an empty folder to prod. **Part 1** (steps 1–4) creates the repos and a local cluster and ships a first endpoint to dev. **Part 2** (steps 5–7) adds a Postgres database and a Next.js web UI with one system spec shipped across three repos. **Part 3** (steps 8–12) adds staging, observability, a release from the tested builds, prod with daily backups, and a restore drill. Each part runs in a fresh Claude Code session (`/clear`): every command keeps its state in the repos. Every step is one sentence in Claude Code: say what you want in your own words and Claude runs the matching slash command, or type the command yourself. Each step shows both. Open a step to jump the recording there and see what was typed, what Claude asked, what it did and the result. Each step links to the real pull requests in the public demo repos [taskboard11-api](https://github.com/ika100-demo/taskboard11-api), [taskboard11-web](https://github.com/ika100-demo/taskboard11-web) and [taskboard11-gitops](https://github.com/ika100-demo/taskboard11-gitops), so you can check every claim.

## About the timing

Every time on this page is wall-clock time with CI rounds included. Nobody watched this run: Claude Code typed the sentences and took the suggested answer to the three questions the run asked and to its one stop, so a person's time is the 4 minutes those answers and the gaps until the next sentence took. **Part 1 took 28 minutes, part 2 59 and part 3 43**, 130 in all; the recording shows them in under 5 minutes. Earlier runs, and what changed in the platform between them, are in [Performance measurements](/sdlc-foundry/reference/performance/).

**What was edited:** waiting is cut and the host name in the status bar is blanked. Nothing else is changed. The journey was recorded with [asciinema](https://asciinema.org) on 2026-11-12 with sdlc-foundry 5.18.0, in the public demo organisation [ika100-demo](https://github.com/ika100-demo); Claude Code typed the sentences on the user's behalf in the same recorded terminal. The observability PR, which a platform defect held back, was finished after the run on 5.19.0 and is not in the recording.

## Background: timing in detail

All times are minutes, measured from the recording, the journey record (`cplat platform runs journey`), the session transcripts and the GitHub Actions runs of the demo repos. The platform's goal is a journey of 60 minutes ([spec 136](https://github.com/ika100/sdlc-foundry/pull/489)).

**Per step:**

| # | Step | Minutes | Agents working | Waiting | Tokens | What takes the time |
|---|---|---|---|---|---|---|
| 1 | Create the system | 1.5 | 1.3 | 0 | 0.3 M | two repos from their templates |
| 2 | Merge, cluster and expose | 5.4 | 1.1 | 3.9 | 0.7 M | the cluster, two CI rounds, the first deploy |
| 3 | Write and approve the spec | 4.3 | 2.0 | 2.0 | 0.9 M | the approval with 8 assumptions, one CI round |
| 4 | Ship the spec | 16.7 | 10.2 | 6.5 | 5.7 M | plan, acceptance tests, coders, a mutation check, one PR, deploy and smoke |
| 5 | Add a web UI | 6.0 | 1.9 | 3.9 | 0.7 M | a new repo from its template, one CI round, a deploy |
| 6 | One spec for the whole system | 5.3 | 2.9 | 1.8 | 1.4 M | one open question (a login), the approval, one CI round |
| 7 | Plan and ship it to dev | 47.7 | 29.0 | 17.9 | 16.8 M | two repo sessions building in parallel, the stop for the plan decision, one landing, deploy and smoke |
| 8 | Hosts, observability and staging | 8.9 | 2.6 | 6.1 | 1.9 M | four PRs, staging promotion and smoke |
| 9 | Release | 7.7 | 3.6 | 3.8 | 2.9 M | gates and image scans in two repos, tags on the staging commit, two follow-up PRs |
| 10 | Backups and the prod PR | 5.5 | 1.7 | 3.6 | 1.9 M | the backups bucket, one prod PR for both components |
| 11 | Prod | 7.4 | 0.5 | 6.6 | 0.7 M | the merge, Argo CD rolling out a three-instance Postgres, smoke, the "Prod check" task |
| 12 | Restore drill | 13.9 | 2.1 | 11.5 | 1.3 M | the restored copy (9.5 minutes of waiting for it), the check, the discard |

Tokens per step count every session of the run: the three sessions that typed the sentences, their subagents and the repo sessions of the system ship.

**Where the wall clock went** (each minute counted once, from the session transcripts; agent work counts first):

| Share | Minutes |
|---|---|
| A person | 4 (3 %): the answers to three questions and one stop, and the gaps until the next sentence |
| Waiting, no agent working | 68 (52 %): CI checks and merges 26, deploys and Argo CD 21, restores 9.5, promotions 4.4, the cluster 2.3, unexplained 4 |
| Agents working | 59 (45 %): the sessions that typed the sentences 39, the system ship's repo sessions and subagents 20 |

**CI, as GitHub measured it:** 159 Actions runs (2 failed), 131 minutes of run time summed and 6 minutes in queues; CI was running during 54 of the 130 minutes.

**Tokens:** 35 M in 639 API calls: 34.7 M read (95 % of them from the cache) and 0.29 M written by the models; about $17 at Claude API list prices. "Plan and ship it to dev" used almost half of them.

**What the run found:** the plan check let a task through that could not pass before the next one ([#681](https://github.com/ika100/sdlc-foundry/issues/681), the run's one stop); the generated log-tailer checksum failed the gitops repo's secrets scan ([#678](https://github.com/ika100/sdlc-foundry/issues/678), fixed in 5.19.0); the system ship reported a repo's stop about ten minutes late ([#684](https://github.com/ika100/sdlc-foundry/issues/684)); the web template's base image carries a critical zlib CVE ([#682](https://github.com/ika100/sdlc-foundry/issues/682)); and checking a restored copy needed a direct `kubectl` query ([#683](https://github.com/ika100/sdlc-foundry/issues/683)).
