One system, recorded in one run from an empty folder to prod. **Part 1** (steps 1–4) creates the repos and a local cluster and ships a first endpoint to dev. **Part 2** (steps 5–7) adds a Postgres database and a Next.js web UI with one system spec shipped across three repos. **Part 3** (steps 8–12) adds staging, observability, a release from the tested builds, prod with daily backups, and a restore drill. Each part runs in a fresh Claude Code session (`/clear`): every command keeps its state in the repos. Every step is one sentence in Claude Code: say what you want in your own words and Claude runs the matching slash command, or type the command yourself. Each step shows both. Open a step to jump the recording there and see what was typed, what Claude asked, what it did and the result. Each step links to the real pull requests in the public demo repos [taskboard16-api](https://github.com/ika100-demo/taskboard16-api), [taskboard16-web](https://github.com/ika100-demo/taskboard16-web) and [taskboard16-gitops](https://github.com/ika100-demo/taskboard16-gitops), so you can check every claim.

## About the timing

Every time on this page is wall-clock time with CI rounds included. Nobody watched this run: Claude Code typed the sentences and took the suggested answer to the three questions the run asked, so a person's time is the 3 minutes those answers and the gaps until the next sentence took. **Part 1 took 28 minutes, part 2 44 and part 3 32**, 104 in all; the recording shows them in under 4 minutes. Earlier runs, and what changed in the platform between them, are in [Performance measurements](/sdlc-foundry/reference/performance/).

**What was edited:** waiting is cut and the host name in the status bar is blanked. Nothing else is changed. The journey was recorded with [asciinema](https://asciinema.org) on 2026-11-14 with sdlc-foundry 5.22.1, in the public demo organisation [ika100-demo](https://github.com/ika100-demo); Claude Code typed the sentences on the user's behalf in the same recorded terminal.

## Background: timing in detail

All times are minutes, measured from the recording, the journey record (`cplat platform runs journey`), the session transcripts and the GitHub Actions runs of the demo repos. The platform's goal is a journey of 60 minutes ([spec 136](https://github.com/ika100/sdlc-foundry/pull/489)).

**Per step:**

| # | Step | Minutes | Agents working | Waiting | Tokens | What takes the time |
|---|---|---|---|---|---|---|
| 1 | Create the system | 1.7 | 1.3 | 0 | 0.3 M | two repos from their templates |
| 2 | Merge, cluster and expose | 5.9 | 1.0 | 4.5 | 0.7 M | the cluster (2.4), two CI rounds |
| 3 | Write and approve the spec | 3.8 | 1.7 | 1.7 | 0.9 M | the approval with 9 assumptions, one CI round |
| 4 | Ship the spec | 16.7 | 10.9 | 5.8 | 8.6 M | plan, acceptance tests, coders, a mutation check, one PR, deploy and smoke |
| 5 | Add a web UI | 6.0 | 1.5 | 4.3 | 0.8 M | a new repo from its template, one CI round, a deploy |
| 6 | One spec for the whole system | 5.7 | 3.1 | 2.0 | 1.5 M | one question (no login), the approval with 10 assumptions, one CI round |
| 7 | Plan and ship it to dev | 32.8 | 23.0 | 9.7 | 16.9 M | the plan, two repo sessions building in parallel, a second API CI round after a Linux-only test-helper fix, one landing, deploy and smoke |
| 8 | Hosts, observability and staging | 9.9 | 1.6 | 8.1 | 1.2 M | four PRs, staging promotion and smoke |
| 9 | Release | 4.3 | 1.9 | 2.2 | 1.4 M | tags on the staging commit, two follow-up PRs; no local gates, CI already passed them |
| 10 | Backups and the prod PR | 5.2 | 1.0 | 4.1 | 1.2 M | the backups bucket and the daily backup, one prod PR for both components |
| 11 | Prod | 5.9 | 0.7 | 4.9 | 0.7 M | CI on the prod PR, Argo CD rolling out, smoke, the "Prod check" task |
| 12 | Restore drill | 6.6 | 1.2 | 5.4 | 0.9 M | an on-demand backup, the restored copy (2.7 minutes of waiting for it), the query, the discard |

Tokens per step count every session of the run: the three sessions that typed the sentences, their subagents and the repo sessions of the system ship.

**Where the wall clock went** (each minute counted once, from the session transcripts; agent work counts first):

| Share | Minutes |
|---|---|
| A person | 3 (3 %): the answers to three questions and the gaps until the next sentence |
| Waiting, no agent working | 52 (50 %): CI checks and merges 22.5, deploys, Argo CD and smoke 16, promotions 4.8, restores 2.8, the cluster 2.4, unexplained 4 |
| Agents working | 49 (47 %): the sessions that typed the sentences 33, the system ship's repo sessions and subagents 16 |

**CI, as GitHub measured it:** 167 Actions runs (2 failed), 109 minutes of run time summed and 6 minutes in queues; CI was running during 44 of the 104 minutes.

**Tokens:** 35 M in 627 API calls: 34.6 M read (95 % of them from the cache) and 0.28 M written by the models; about $17 at Claude API list prices. The sessions that typed the sentences ran on Claude Opus 5.5. "Plan and ship it to dev" used half of them, "Ship the spec" a quarter.

**What the run found:** no defect that stopped it, and the fixes since journey 13 held: the build check took the tester's commit, the findings took a merged task, the observability command printed the Grafana URL, the web release needed no workaround, no test run hung, and every local URL used the cluster's real port. One gap: the API's landing step escalated a Linux-only fix of a test helper, because it counts any helper change as a weaker test; Claude settled it with the suggested answer within a minute, and spec 200 lets the landing step make such a fix itself.
